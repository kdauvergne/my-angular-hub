📐 Les Modèles de Données (/models)

Structurez vos données métier avec TypeScript en centralisant vos interfaces et classes dans un dossier dédié.

📁 1. Pourquoi créer un dossier src/app/models/ ?

🎯 Source Unique de Vérité

Évitez de redéfinir la structure d'un utilisateur ou d'un produit dans chaque composant. Si une propriété change côté API, vous ne modifiez qu'un seul fichier .model.ts.

🛡️ Sécurité & Autocomplétion

Fini les types any ! L'éditeur (VS Code) suggère automatiquement les propriétés exactes dans vos services TypeScript et vos templates HTML (@for, interpolations).

🧹 Architecture Découplée

En isolant les modèles dans app/models/, vous évitez les imports circulaires entre vos services et vos composants.

Convention de nommage Angular

Bien que TypeScript accepte n'importe quel nom de fichier, la convention professionnelle consiste à suffixer vos fichiers par .model.ts (ex: user.model.ts) et d'exporter explicitement chaque structure avec le mot-clé export.

💡 Astuce : Le fichier baril (index.ts) Un fichier models/index.ts contenant export * from './user.model'; permet de regrouper tous vos imports sur une seule ligne propre : import { User, Product } from '../models';.

⚔️ 2. Exporter une interface vs une class

Option A : export interface

90% des cas (API / JSON)

Une interface décrit uniquement la forme attendue d'un objet. Elle n'existe qu'à la compilation (0 octet ajouté au bundle JavaScript final) et correspond parfaitement aux données JSON reçues via HttpClient ou Firestore.

Option B : export class

Logique métier & Défauts

Une class existe réellement au runtime. Utilisez-la lorsque vous devez instancier un objet avec new, initialiser des valeurs par défaut ou embarquer des méthodes de calcul (ex: getPriceTTC()).

Caractéristique export interface export class
Présence dans le code JS compilé ❌ Aucune (effacée après vérification TypeScript) ✅ Oui (génère une fonction constructeur ES6)
Méthodes et getters (getFullName()) ❌ Signatures uniquement (pas d'implémentation) ✅ Oui, directement appelables sur l'instance
Valeurs par défaut à la création ❌ Non ✅ Oui, via le constructor
Compatibilité directe avec http.get<T>() ✅ Immédiate (le JSON respecte le contrat) ⚠️ Nécessite un .pipe(map(d => new Model(d)))

🔗 3. Exploiter vos Modèles dans Angular

Un flux typé de bout en bout

Une fois votre modèle exporté depuis src/app/models/, il sert de contrat entre toutes les couches de votre application :

  • Dans les Services : type les retours de HttpClient (get<User[]>) et les paramètres envoyés (CreateUserDto).
  • Dans les Signals : garantit le type contenu dans signal<User[]>([]).
  • Dans les Composants enfants : sécurise les entrées via input.required<User>().

🎯 Bonnes pratiques à retenir

1. Interface par défaut Pour représenter des données provenant d'une API REST ou de Firebase, privilégiez toujours export interface : c'est plus léger et idiomatique en Angular.
2. Types Utilitaires (DTO) Utilisez Omit<User, 'id'> pour la création et Partial<User> pour la mise à jour au lieu de créer 3 interfaces quasi identiques.
3. Pas de préfixe "I" Selon le guide de style officiel TypeScript / Angular, nommez votre interface User et non IUser.
